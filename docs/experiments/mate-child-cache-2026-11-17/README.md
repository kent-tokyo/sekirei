# 詰み探索の費用調査：表参照を33.4%減らし、既知6問で約8.0%短縮

2026-11-17。#291で採用済みの整数ハッシュを含む`9f3539f29d6ab85fbe75a733953f271e633eca7f`を基準に、
ユーザーの続行指示に基づいて調査した。終端情報と確定した境界情報を一つの表にまとめるF01は、
既知6問の時間中央値合計を58.793msから54.092msへ短縮した。初手・探索節点・完全着手数は同じで、
新しく生成した全応手証明6件も基準版の別プロセスで検証できた。

事前の10%進行条件には届かず、登録済み判定は`NO_PASS`。
ただし、この10%は担当エージェントが置いた便宜的な進行基準で、統計的な有意差の境界ではない。
結果を受けてユーザーから条件の厳しさを指摘された。約8%の短縮を「改善なし」と扱う根拠はなく、
候補は別入力での確認に値する。この初回記録の結果や判定は変更しない。
この初回記録では共有エンジンに適用していない。独立確認の課題を[issue #293](https://github.com/kent-tokyo/sekirei/issues/293)に記録した。その後の別入力確認は[F01 C01](F01_C01.md)を参照。

合計短縮は7.996%、4問改善・2問微増。最大時間の11/14題を除いても5.950%短縮した。
11/14題は両版とも長い計測値を含み、既知6問・各5回だけでは効果の一般性や精度を確定できない。
問題ごとのRSS増は最大180,224バイトで、登録した退行条件には該当しなかった。

## 回数は何が減ったか

F01で減ったのは`lookup_with_dependency`内の`map.get`呼出しで、
6問合計3,744,027回から2,494,213回へ33.382%減った。書込みや初期化は数えていない。
完全な着手適用は両版とも632,305回。探索節点も全件一致し、11/14題は46,297のまま。
今回の変更は同じ探索を安く実行するもので、探索節点が最小になったという証明ではない。

別候補K01では、順序付き合法手と子ハッシュの再生成をキャッシュで省く余地を先に測った。
最大8,192局面・65,536子の条件で、省略候補は87,130回、完全着手の13.780%だった。
事前の20%条件に届かず、速度比較を行う前に停止した。
従来処理を省かず再生成して一致を確認する診断なので、これは実現した削減率でも速度測定でもない。
20%も作業量を絞るための便宜的な基準であり、これだけでキャッシュが無益とは判断できない。

## 正しさと測定の範囲

F01は終端を優先する規則と、深さ・反復依存・中断・矛盾境界の扱いを保持した。
終端と境界は別フィールドを更新し、互いを消さない。差分の独立レビューでも致命的な欠落はなかった。
詰み探索の通常テスト38件と明示的なignore回帰1件が通過した。
6件の新証明木は以前の保存木とSHA-256まで一致し、基準版のcheckerでも全件再生できた。

Apple M4/16GiB、AC、1T、評価重みなし。開始前はメモリ空き66%、ディスク空き15GiB、
熱・性能警告なし。比較中はエンジンを逐次起動した。
探索上限999,999、深さ25、内部8秒・外側12秒、RSS2GiB。
計数版12起動と計数なし版60起動を分離し、速度には後者の内部探索時間だけを用いた。
証明生成6起動と基準checker6起動を含め、全プロセスの終了を確認した。
通常探索の棋力、最短詰み、他エンジンとの新たな速度倍率は調べていない。

F01を選ぶ前のCPU診断P01では、11/14題を100回解く間に2秒間サンプリングした。
1,527スタック中475が`lookup_with_dependency`の最上位フレームだった。
関数単位の概算であり、個々の表参照がCPU時間の31.1%を占めると特定したものではない。
