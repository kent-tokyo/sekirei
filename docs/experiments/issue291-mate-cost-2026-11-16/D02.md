# 291-D02：探索本体のCPUサンプル診断

2026-11-16。前試行のC01は完全着手を86%以上減らしても、既知6問の回答時間を5.10%しか短縮しなかった。この差を説明するため、固定ソース`14586edaf3a5e9e03739c2fa39c9e3f48e2cd56c`の無改変ソルバーをシンボル付きreleaseでビルドし、11/14題を同一プロセスで100回順次解く間のCPUスタックを`/usr/bin/sample`で採る。入力は既知の診断題で、候補の採否には用いない。

仮説：完全着手よりも、合法手・王手生成または表の検索・集約にCPU時間が集まる。最小の検査は2秒・1ms間隔のサンプル1回。`solve_mate`の各回答が既存の初手`3b2a`、nodes`46297`と一致することを確かめる。サンプルは関数別の概算であり、個々の処理の正確な割合や改善率を示さない。内聯化などで識別できない場合はそのまま停止し、推測で候補を作らない。

条件：1T、NNUEなし、深さ25、各呼出し上限999,999訪問・内部8秒、外側30秒、RSS 2GiB、出力32MiB。ビルドは単一ジョブ・5分、追加領域2GiB。実行前に他ジョブ、メモリ、空き容量を確認する。`sample`で必要な権限が得られない場合は未測定と記録する。C01/O01の成績を再試行しない。登録・バイナリ・入力・ツール・出力のハッシュを保存してから判定する。

この診断で探索の費用を絞れた場合のみ、単独変更の規則と既知題の進行条件、独立入力での確認条件を別契約に固定する。#291の既定変更、採用、クローズはこの診断だけでは行わない。

## 結果

[登録](d02-registration.json)後、100呼出しがすべて同じ初手・nodesで完了し、ドライバーは5.309秒で正常終了した。[receipt](d02-receipt.json)と生サンプル`data/runs/issue291-d02-20261116/sample.txt`を保存した。`sample`は2秒間で1,526スタックを採取し、計測時の物理メモリ最大値は9,072KiB。関数名の識別に成功した。

排他的な最上位フレームでは、`Solver::lookup_with_dependency`が409、標準`DefaultHasher`とその`BuildHasher`のフレームが計324で、合計733/1,526（48.0%）を占めた。`move_gives_direct_check`は190、`Solver::children`は90。`Solver::mid`内にインライン化された処理もあるため、各機能の正確なCPU割合とはしない。今回のサンプルは11/14題だけで、他の5題への一般化も未確認。

ハッシュ表へのアクセスが費用候補と分かった。次の単独候補は`Solver`のローカルな3表だけのハッシュ計算を変え、表のキー・値、検索順、証明条件を保つ。安全性と既知題での時間改善を別に検証する。
