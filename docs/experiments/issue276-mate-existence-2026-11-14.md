# Issue #276: 有界な詰み存在証明と全応手証跡

## 実装前の問いと最小検査

高速 `solve_mate` の証明表は局面hashだけを鍵にし、残り手数と経路反復を鍵に含まない。表の初手をそのまま「全応手の証明」と呼べない。探索表を候補木の抽出にだけ使い、別の節点上限で合法手を再生成して全応手を再生検証すれば、最短性を要求せずに証明済み手順を公開できるか。

公開issueの⑤⑥⑦の3局面を最大17手・探索100万節点、抽出と検証はそれぞれ2万節点で確認する。中断、不正局面、探索不成立は `Unknown` 相当として扱い、完全な不詰を主張しない。既存の `solve_mate` と `analyze_mate_with_policy` の契約は変更しない。

## 追加API

`mate::prove_mate_existence` は探索・候補木抽出・合法再生を別上限で実行する。`tree` が `Some` になるのは、再生検証で攻方の連続王手、玉方の全合法応手、全葉の詰み、経路反復なし、最大手数を確認した場合だけ。`stop_reason` は探索節点、探索期限、未証明、抽出節点・未完成、検証節点・不成立を分ける。`mate::verify_mate_proof_tree` を外部から再実行できる。代表手順と証明木の最長枝は、最短詰み距離や初手唯一性ではない。玉方の無駄合も全合法応手に含む。

## 検証と残る制約

公開3局面は16MiBスタックのテストスレッドで各1件の検証済み木を取得し、代表初手 `L*3e`、`N*2c`、`6c7c`、最長17手以内を確認した。片玉・両玉、先後、成り・不成、違法な打ち歩詰め、全応手の欠落、node limit 0/1、探索期限、抽出/検証打切り、経路反復、元盤面復元を対象テストに含む。

深い公開図⑤は標準2MiBのdebugテストスレッドでstack overflowした。追加APIを呼ばず既存 `solve_mate` だけを呼んでも同じ図で再現し、既存Solverの再帰経路に由来する。17手の検証は16MiBスタックで行った。小さいスタックの呼出元での安全性は証明していない。通常探索の棋力改善や高速solverと完全最短探索の速度倍率も主張しない。

公開 `main` の `57f85130` と同じ木を基点にした隔離ブランチで、coreライブラリテスト476件通過・10件無視、workspace全targetのClippyと整形を通した。局所 `mate::tests` 28件の `cargo-llvm-cov 0.8.7` 計測では追加実装265行中253行を実行した。これは全workspaceの98%ゲート判定ではなく、未実行経路の確認に使った。入力不正の再生、証明なし、合法だが王手でない手の拒否を追加テストで確認した。
