# Issue #291：子ハッシュ取得の重複着手から詰み探索の費用を減らす

作成日：2026-11-16。状態：**P0～P4の初回試行は採用候補なしで停止。その後の続行指示によるD02/H01で独立確認を通過し、統合候補を反映。結果は[判断記録](../experiments/issue291-mate-cost-2026-11-16/DECISION.md)。**

[Issue #291](https://github.com/kent-tokyo/sekirei/issues/291)の第一候補は、子局面のハッシュを読むためだけの着手・取り消しを、盤面を変更しない計算に置き換えること。先に完全着手数の内訳を測り、探索結果を保って削減できる費用を確定する。その後、必要なら指し手順序と初期推定を別々に調べる。

今回の依頼は計画作成まで。これは11月16日のリセット後に依頼された新しい費用調査の計画であり、旧計画の継続条件を引き継がない。通常探索の#280、NNUE学習、対局、既定採用は本計画の実行範囲に含めない。

## 現行コードから最初の変更を絞る

確認したソースは `14586edaf3a5e9e03739c2fa39c9e3f48e2cd56c`。計画作成時、`crates/sekirei-core`に未コミット差分はなかった。[既存比較](../experiments/jsa_tsume_2026-11-16/komoring_comparison/README.md)の入力・有効receiptのSHA-256は、issueの記載と一致した。

11月14日題では、Sekireiの完全着手429,395回に対して`Solver::mid`訪問は46,297回だった。6問中5問は外部エンジンの完全着手が少なく、11月7日題はSekireiの38回が最少だった。この差のどこまでが重複処理によるかは、まだ測れていない。

| 区分 | 現行の処理 | 調べること |
|---|---|---|
| 王手生成 | [mate.rs](../../crates/sekirei-core/src/mate.rs) `Solver::children`、721–740行。直接王手は静的判定、開き王手候補は着手して確認 | 開き王手判定に使う完全着手数 |
| 子ハッシュ取得 | 同 `mid`、766–774行。生成された全子手を着手・取り消し | 探索しない子にも払っている更新費用 |
| 選択子へ降下 | 同829–831行。同じ手を再び着手して再帰 | 本来の探索に必要な更新回数 |
| 回答構築 | 同 `solve_mate`、634–641行。王手を再生成し、着手して証明表を照合 | 回答初手を選ぶまでの追加費用 |

`mid`の一回の呼出し内では子ハッシュ配列を再利用する。重複生成は再訪時に発生するため、「ループの各周回で全子を着手する」とは数えない。合法手生成の通常経路も、全手を完全着手して検査する構成ではない。

## 工程は計数、等価な置換、比較の順に進める

実装・計測は担当者1名が逐次実行する。独立レビュー担当は計数漏れと正しさを点検し、エンジンジョブを並行起動しない。

| 工程・ID | 前提と作業 | 成果物・完了条件 |
|---|---|---|
| P0／291-B0 | 固定ソースの隔離checkoutを用意。入力、既存証明木、計測器、コンパイラ、ビルド条件を照合し、実行前に登録 | `registration.json`。既存試行と新試行の保存先を分け、共有作業ツリーの差分を取り込まない |
| P1／291-D01 | 既存の完全着手カウンターに用途別の区分を追加。6問を各3回測る | 区分の合計が総数と一致。各問の総数・初手・標準nodesが既存結果と一致。費用の内訳表を作る |
| P2／291-C01 | 子ハッシュの直接計算を実装し、ハッシュと状態の等価性を先に検査 | 合法手の予測ハッシュ＝実際の着手後ハッシュ＝全盤面からの再計算。盤面不変、既存詰み回帰テスト成功 |
| P3／291-AB01 | B0とC01を同じ入力・条件で比較。計数版と計数なし版を分ける | 完全着手、標準nodes、時間、メモリ、証明、退行を含む判定。未完了も残す |
| P4／条件付き | 内訳とC01後の残存費用を見て、順序・初期推定の診断を行う価値を判断 | 下記の条件で単独変更を最大2件。実施しない場合も根拠を記録 |
| P5／解決判定 | 再現手順、原因として確認できた範囲、候補の採否理由をまとめる | レビュー可能な差分と結果表。既定統合は独立確認後。issueのクローズは完了条件を満たした後 |

P0は既存の`prepare_counted.py`、`search_driver.rs`、`run_comparison.py`、`verify_comparison.py`を再利用する。固定出力先を持つ既存スクリプトは直接再実行せず、新しい試行ID・出力先へ限定した変更を加える。無効だった初回比較のログも保存する。

P1の総数は`Board::do_move_impl`入口で数える。王手生成、子ハッシュ、降下、回答構築を相互排他的に分類する。回答構築中の王手生成も二重計上しない。未分類を別項目として残し、0になるまで計数の解釈を確定しない。undo、null、部分的な歩打ちプローブ、初期化、後段の証明検証は従来どおり対象外。再訪数、生成手数、表のエントリ数は補助値とし、計数版の時計を速度判定に使わない。

## C01は探索順を保ち、ハッシュだけを計算する

仮の内部APIを`Board::hash_after_legal_move(&self, mv)`とする。既存の[board.rs](../../crates/sekirei-core/src/board.rs)と[zobrist.rs](../../crates/sekirei-core/src/zobrist.rs)のキー差分を使い、手番、移動元・先、成り、捕獲駒の成り戻し、持駒枚数の増減を反映する。対象は生成済みの合法手とし、公開APIの追加は必要性を見て決める。

置換するのは`mid`の子ハッシュ取得と`solve_mate`の回答照合。王手判定、再帰時の着手、証明木の抽出・検証は既存の処理を使う。指し手順序、未登録値`(pn,dn)=(1,1)`、表のキー・再利用条件、追加キャッシュを同時に変更しない。

通常手、成り・不成、成駒捕獲、7種類の打ち、持駒枚数の境界、双方の手番、玉移動、片玉問題を含む小さな固定ケースを検査する。固定seedの合法局面列も追加し、最大10,000合法着手を照合する。ハッシュだけでなく、盤面・持駒・手番・手数・NNUE累積値の不変、続く合法手生成との整合も確認する。実際の着手・取り消しは合法性キャッシュを無効化するため、それを省く影響も確認対象にする。

#287の検査では、次を維持する。

- 未完了表は`(hash, remaining)`をキーにする。
- 証明済み結果は残り手数が増える方向、不証明は減る方向だけに再利用する。
- 反復依存・中断・未完了の結果を、独立した完了結果へ昇格させない。
- 経路上の反復を優先し、OR/ANDごとの依存伝播と矛盾境界の無効化を保つ。

これらは既存の保証を維持する条件である。現行コードが留保している表の履歴依存全体を、この最適化で解消したとは扱わない。

## 時間と完全着手数の両方で判定する

既知6問を一件も除かず、C01の計数版を各3回、B0/C01の計数なし版を各5回測る。問と反復ごとにA/B順を反転し、毎回新規プロセス・空の表とする。時間の主指標は同一Rustドライバー内の`solve_mate`開始から戻りまで。外側のIPC・終了待ちは別記する。

C01の機構確認は、全6問で初手・標準nodesが一致し、完全着手の減少が除去したハッシュ照合の回数と一致すること。時間制限に達した測定で一致を要求せず、その試行は未完了として扱う。成功扱いにするための上限延長は行わない。

開発段階で統合検討へ進める目安は、全6問の時間中央値の合計が10%以上減り、各問の悪化が`max(B0中央値の10%, 0.1ms)`以内、ピークRSS増加が`max(B0の10%, 1MiB)`以内であること。各問の中央値・範囲、改善/悪化数、最大時間の1問を除いた集計も併記する。これは既知入力での進行条件であり、一般的な速度資格ではない。ばらつきが大きければ時間差は未確定とし、反復を増やして通過を狙わない。

変更後の全6問で`prove_mate_existence`から証明木を再生成し、全合法応手、連続王手、詰み葉、反復、復元を別段階で検証する。保存済みの証明木を読むだけでは、候補の探索の正しさを十分に確認したことにならない。これらの時間と完全着手数は、初手回答までの計測へ加算しない。

## 順序と初期推定は必要な場合だけ単独で調べる

C01後も再訪や降下の費用が大きければ、未登録値がすべて`(1,1)`で同値を生成順に選ぶ影響を調べる。固定したKHソースの`initial_estimation.hpp`と`local_expansion.hpp`を参照し、次の二つを分ける。

1. **順序だけの診断**：初期値を`(1,1)`のまま保ち、同値候補の優先順だけを変更する。
2. **初期推定だけの診断**：生成順を保ち、未登録の子に与える正の有限pn/dnだけを変更する。

各診断はB0に対する単独変更とし、C01とも合成しない。優先規則または推定式は、P1で確認した費用と固定KHソースを根拠に一つ選び、コード差分・定数・進行条件を登録してから測る。結果を見て定数を調整しない。C01と異なり初手・nodesが変わり得るため、別の初手も全応手証明で検査する。共通の時間・RSS・退行条件に加え、完全着手数の6問合計10%以上減、各問の増加25%以内を進行条件とする。

初期推定を変える場合は、候補の選択・集約と、選択子へ渡す閾値計算で同じ値を使う。片方だけ変えると`th_dn - dn + cd`などの減算が成立しなくなるため、減算の下限と`INF`への飽和をテストする。終端・証明済み・反復の値を推定値で上書きしない。

持駒優劣の再利用、二重計上抑制、高速1手詰の追加は、この初回計画では実装候補にしない。残存費用を説明する根拠が得られた場合に次の提案として記録する。外部エンジンとの差を、一つの機構だけの効果とは解釈しない。

## 実行には小さな資源上限を置く

既存比較と同じ1T、評価重みなし、深さ25、`solve_mate`の訪問上限999,999、内部期限8秒、外側12秒を使う。証明APIの探索上限は1,000,000、抽出・検証は各100,000。各子プロセスのRSSは2GiB以下、ログは2MiB以下とし、超過時は自分のプロセス群を終了・回収する。

P1〜P3を最初の一区切りとし、ソルバー起動は計120回以内、診断全体の経過時間は20分以内。ビルド・テストは別枠で各コマンド5分、合計15分まで、ビルドジョブは1。ログ総量128MiB、追加ビルド領域2GiBを上限とする。開始前に他ジョブ、メモリ、温度、空き容量を確認し、追加領域を含め4GiB以上の空きを必要とする。資源不足時は他作業を停止・削除せず、未実行範囲を記録する。

P4へ進む場合は各候補に別IDを付ける。各候補は計数18回、B0との計数なし比較60回、候補証明6回の最大84回・20分以内とし、同じメモリ・出力上限を適用する。技術的な失敗は原因と修復を確認した別試行だけを許す。性能不通過の再試行や、結果を得るための予算拡大はしない。

ローカルでは新規ハッシュ検査に加え、`cargo test -p sekirei-core --lib mate::`、`cargo test -p sekirei-core --lib hash_roundtrip`を行う。NNUE有効時の検査は`cargo test -p sekirei-core --test halfkp_incremental`を別プロセスで実行し、新APIの累積値不変も検査する。ignore指定の`existence_proof_handles_fourth_public_diagram_within_fixed_budget`は、coverageなしで明示実行する。統合候補になった段階で[開発手順](../development.md)のfmt・workspace test・clippyと必要なCIを実行する。カバレッジ計測を各診断反復に含めない。

## 原因説明と独立確認をそろえて解決を判断する

調査の完了条件は、6問の完全着手を用途別に説明でき、計測追加による探索変更がないと確認できること。そのうえでC01の結果と、順序・初期推定を試したか見送ったかの理由を残す。

修正の統合には、候補を凍結した後、既知6問と旧計画の保留集合を除く未使用入力で独立確認する。入力の選び方、件数、時間・退行条件を独立確認の結果を見る前に別契約で固定する。既定採用の条件を既知6問の通過で代用しない。通常探索へ広げる場合の独立H1や棋力検証も別件とする。

安全で効果のある修正が独立確認とレビューを通れば、再現手順・結果・修正をまとめたPRで#291を閉じる。予算到達、時間差未確定、改善なしの場合は、その結果と残った問いを記録して止める。計画作成や試行の終了だけを理由にクローズしない。

この節までを実行前の計画とする。実行後の条件・結果・停止理由は[判断記録](../experiments/issue291-mate-cost-2026-11-16/DECISION.md)へ追記した。結果に合わせて上記の進行条件と上限は変更していない。続行指示による別診断と候補の条件は[D02](../experiments/issue291-mate-cost-2026-11-16/D02.md)、[H01](../experiments/issue291-mate-cost-2026-11-16/H01.md)、[独立確認](../experiments/issue291-mate-cost-2026-11-16/H01-CONFIRM.md)に実行前登録した。
