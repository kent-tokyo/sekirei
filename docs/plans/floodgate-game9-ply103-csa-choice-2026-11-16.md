# 第9局103手目で`4e4d`を選ばなかった理由の調査計画

2026-11-16に計画を固定し、同日A〜Cを実施。[結果](../experiments/floodgate_v054_r6_rescue_2026-11-16/CSA_CHOICE.md)は冷起動6回・温め2系列の全8回の103手目で`4e4d`、実戦`4g4h`は再現せず。Dは再現時のみの条件を満たさず未実施。対象はv0.5.4+r6のFloodgate第9局、先手103手目の実戦`4g4h`と候補`4e4d`。既存の[全手番再分析](../experiments/floodgate_v054_r6_rescue_2026-11-16/REANALYSIS.md)では、候補の方が固定root・別探索器・観測応手の範囲で良いが、候補も負の評価である。ここで確かめるのは**Sekireiが実戦手を返した条件**であり、勝敗や棋力の資格試験ではない。

## 最初に訂正する前提

- 実戦の固定v0.5.4 CSA binaryは`Searcher::search_with_history`を呼び、4TはRayonのYBW分岐探索に使う。USIの`SearchMode=Auto`で選ばれる4T Lazy SMPとは別経路。CSAでは局面履歴も探索へ渡している。根拠はタグcommit `1ce96c5a9c87b1ffcb68d86cb74ec3cb27eb474b` の `crates/sekirei-csa/src/protocol.rs` と `crates/sekirei-core/src/search.rs`。
- 実戦契約はCSA binary SHA-256 `1a497f166c6484e6ff63573345988ef6357910d5c24e626523fa954f553fa94c`、r6 SHA-256 `634bdf527e7306045c8278df1d5311777561dfb09c1ebe6829ff3f4d883cc469`、`FV_SCALE=24`、4 Rayon workers、Hash 256MiB、最大深さ50、Fischer legacy。対局の`analysis_dir`はnullで、当時の得点・PV・TT内容は保存されていない。
- 公開CSAと監督ログは103手目の`+4748KI`（`4g4h`）、サーバー計時`T11`を示す。101手目後の自分の残時間は112秒。固定版の`csa_think_budget_ms(112000, 10000, true)`は **11,733ms** を返す。`T11`をそのまま11,000msの探索上限と置かない。
- 既存の私有`analysis/g9p103-lazysmp-root-choice-20261116/`にはUSIの同時間診断12回がある（結果SHA-256 `8bee1904f413304d45ab3ba4cf1a8f062daa75383514ee2945d044c798366571`）。103手目の1Tは`4e4d`が3/3、4T Lazy SMPは`4e4d`が2/3、`L*4h`が1/3で、実戦`4g4h`は0/6。この診断はHash64・USI経路なのでCSAの原因判定に流用せず、繰り返さない。

## 問い、実行条件、停止規則

計算前に競合job、メモリ圧迫、空き容量を確認する。実行は隔離したv0.5.4 tag checkoutから1jobずつ、最大4 Rayon workers、同時エンジン1個、RSS 1.5GiB、結果128MiB以内。新しい試行IDと入力CSA/履歴/SFEN、source・binary・重みSHA、実行設定、下記の分岐規則を私有manifestへ固定する。診断全体は**最大14探索呼出し・合計240秒**、ビルドが必要なら別枠1job・5分・追加出力1GiBまで。ホストの時間条件が崩れた実行は探索的と記録し、厳密な同時間比較へ算入しない。上限・資源圧迫・不正な履歴/評価ロードで停止し、結果に合わせて上限を延長しない。

| 段階 | 最小の問いと手順 | 最大探索数・判定 |
| --- | --- | --- |
| A. 実戦条件を固定 | 公開/保存CSAと監督ログ、103手目直前のSFEN・102手の履歴、残時間112秒、割当11,733ms、実戦binaryとr6のhashを再照合。CSAが使う探索入口、TT/履歴表の寿命、YBWの有効条件をタグのコードで確認 | 読取りのみ。どれか不一致なら探索前に入力を修正し、旧条件の結果を混ぜない |
| B. CSA経路で冷起動 | 小さな隔離adapterでタグ版`Searcher::new(Tt::new_for_evaluation(256, true))`、`search_with_history`、`SearchConfig`最大深さ50・11,733ms、r6/24、102手履歴を使う。Rayon 4Tと1Tを各3回、毎回新しいプロセスで交互に実行 | 最大6呼出し。実戦`4g4h`が出る頻度、完了反復の手/得点/深さ/PV/停止理由、節点、hashfullを保存。出なければ「冷起動では再現せず」 |
| C. 直前局面で状態を温める | Bで実戦手が出ない場合だけ、同じ`Searcher`を保持して実戦99・101・103手目を順に探索。相手手はCSAどおり合法適用し、各自手には固定版の時計式から11,800・11,766・11,733msを与える。4Tで最大2系列。TTと履歴表を保持したまま103手目を比較 | 最大6呼出し。これは直前2自手だけの近似であり、実戦の全対局状態や前8局のTTは再現しない。再現しなければこの枠で停止 |
| D. 再現時だけ機構を分ける | BまたはCで実戦手が出た場合だけ、同じCSA入口・重み・履歴を保ち、4TのYBW有効/無効を1対照にする。完了深さごとのroot手と得点を取得する計測は別の計測付き呼出しとして記録し、計測による時間影響を混ぜない | 最大2呼出し。実戦手が消える/残る方向、PV、root候補の扱いを確認。単発の変化は因果の証明にしない |

Bの実装ではUSIバイナリを代用しない。既存`sekirei-search-diagnostic`はTTを64MiBで生成するため、そのままではHash256の対照にならない。必要なadapterはタグ版の公開core APIを呼ぶだけにし、通常探索の手順・定数・重みを変えない。`RAYON_NUM_THREADS`または明示ThreadPoolで実worker数を記録する。最初のBは通常の`search_with_history`を計測なしで呼び、反復traceが必要なDだけ計測付きAPIを使う。ビルドの速さやUSIの節点数をCSA棋力の証拠にしない。

## 判定と次の作業

1. **冷起動で実戦手が再現する場合:** その実行の完了手とPVを確認し、DでYBW分岐の影響を局所対照する。4Tだけの傾向でも直ちに「YBWが原因」とはせず、TT・履歴表・時間停止の違いを残す。
2. **温めた場合にだけ再現する場合:** 直前のTT/履歴表が候補。直前2手の近似と実戦の全履歴状態を区別し、必要な最小のTT対照を次契約にする。`clear_tt`は履歴・評価キャッシュも消すため、それだけでTT単独の因果効果とは呼ばない。
3. **どちらでも再現しない場合:** 今回の固定上限では実戦手を再現できない、と報告して止める。元対局は`analysis_dir=null`で探索PV/TTがなく、過去の1手の厳密な理由を断定しない。次の実戦では既存の`--analysis-dir`で得点・PV・完了深さ・割当時間を保存する。過去の1局面に合わせた探索既定変更はしない。

どの分岐でも、`4e4d`を発見できなかったのか、発見したが低く評価したのか、より深い反復が未完了だったのかを、得点と**その完了反復の手**を一組として記録する。返却手だけを最後の完了得点へ結び付けない。改善案が具体化した後は、この既知局面を開発用に限定し、未使用の別対局・同時間の品質比較と既存の独立採用条件で判定する。今回の計画は新規対局、学習、既定値変更を含まない。
